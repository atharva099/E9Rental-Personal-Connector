# E9Rental Personal Connector — Gmail question answering

## Product vision

The primary product goal is: **A user securely connects their Gmail account, asks a question in natural language, and the application finds relevant authorized Gmail messages and produces an accurate answer supported by source citations.**

The target Personal workflow is dashboard → explicit read-only Gmail authorization → supported question or search → bounded live Gmail retrieval → evidence-grounded answer or structured recent-email rows → inspectable citations or a separately approved Full Email Viewer. The separate Challenge/SANDBOX profile may use its local synchronized index; it is not a fallback for Personal Gmail questions. Follow-up questions should not require manual exports. That last behavior is planned; it is not implemented today.

## Explicit initialization and fail-closed reuse

The documented Personal launcher now defaults to **reuse**, not provisioning. Reuse requires existing nonempty API-token/key/tenant/token/database files. It validates 32-byte Base64 keys, a distinct API token, tenant format, AES-GCM token decryption with exactly gmail.readonly, and read-only H2 access to the existing unified table. Existing rows must match the approved Gmail account and tenant, LIVE mode and Gmail source, including serialized record metadata. Missing/corrupt/inconsistent/in-use stores fail with a safe error before backend startup; no provider request is involved. Runtime paths containing connection-string separators or redirected ancestors are rejected. Unsafe runtime-directory permissions are rejected rather than repaired during reuse. The database URL retains IFEXISTS=TRUE when the backend starts.

First-time setup requires `-InitializeRuntime` and a **previously nonexistent** external directory. Existing directories, even empty ones, are refused. Only this explicit provisioning path generates keys and tenant identity. After creating those artifacts, the initialization-only launcher invokes a separate offline helper that creates the unified H2 schema through `UnifiedRepository.initializeEmptySchema`. The helper requires the explicit initialization marker, the generated Personal tenant, the expected fresh-runtime contents, no existing `unified` directory or Gmail token, and no overlap with the Challenge runtime. It verifies the resulting database file and empty unified-record table. It has no OAuth or provider dependency and imports no historical records. It never runs during ordinary reuse. Initialization still does not fabricate an OAuth token; a separately authorized Gmail OAuth callback must save the encrypted token before normal reuse validation can pass.

### Incomplete runtime recovery

The public release does not include the maintainer-only continuation workflow for an already provisioned but incomplete runtime. Normal startup supports only explicit initialization of a new external runtime or fail-closed reuse of a complete runtime. If reuse reports an incomplete runtime or an initialization-failure marker, preserve the directory unchanged and request separate maintainer review. Do not initialize over it, repair it, or delete it as a recovery shortcut.

If local provisioning or empty-schema initialization fails after creating the new directory, the launcher best-effort creates `.personal-runtime-initialization-failed` with constant, non-secret text using create-new semantics. Reuse rejects this marker before reading or validating runtime artifacts. A failure before directory creation leaves no runtime. If marker creation itself fails, required-artifact checks still reject an incomplete directory; a partial H2 file is preserved for manual review and is never overwritten. No existing runtime is marked, changed, repaired, overwritten, or deleted. Preserve a failed runtime and request manual review; do not rerun initialization against it. Successful key/tenant/schema provisioning is not the same as a reusable runtime: reuse additionally requires the separately authorized OAuth token and successful read-only validation of the existing H2 database. A later Java startup failure is not automatically repaired or deleted; the required-artifact checks still fail closed until the missing artifacts are legitimately established.

```powershell
# First-time provisioning only, after separate approval; use a NEW external directory.
./scripts/Start-Personal.ps1 -PrivateDirectory $privateDirectory -ClientFile $clientFile -ApprovePersonalGoogleAccess -InitializeRuntime
# Subsequent reuse of that completed runtime; no new keys, tenant or database.
./scripts/Start-Personal.ps1 -PrivateDirectory $privateDirectory -ClientFile $clientFile -ApprovePersonalGoogleAccess
```

These checks do not prove live OAuth validity or replace the provider-side identity check. A well-formed API token has no prior trusted fingerprint to compare against; empty tables cannot prove historical account/tenant continuity. No recovery manifest, automatic repair, live permission refresh or migration is introduced. The offline verifier requires exclusive H2 availability and never connects to the running Personal database. Its explicit `--checkpoint-fingerprint` mode opens the existing file with `IFEXISTS=TRUE` and `ACCESS_MODE_DATA=r`, performs no schema creation or repair, and fails closed unless it finds exactly one valid checkpoint scoped to the configured Personal tenant and approved Gmail account. It prints only a stable, URL-safe HMAC-SHA-256 fingerprint; the HMAC key is domain-separated from the local token-encryption key, and the fingerprint includes the scoped checkpoint fields. It does not print the cursor, tenant, account or checkpoint identifiers. Capture its output into a local PowerShell variable and compare it in memory; the fingerprint is a pseudonymous equality token, not a public value. H2 must be exclusively available, so take each snapshot only while the backend is gracefully stopped. For a restart comparison, capture the pre-restart fingerprint while stopped, start normally against the same runtime, then gracefully stop again to capture and compare the post-restart fingerprint; finally start normally again and verify health. Each process stop/start requires its own approval. Keep Drive and Personal WhatsApp ingestion disabled; this verifier supports Gmail-only snapshots. Direct invocation of Java outside the documented launcher does not execute this launcher preflight.

With the existing approved runtime/account variables set privately and the backend stopped, capture the verifier output without echoing it:

```powershell
$beforeOutput = & java '-Dloader.main=com.e9rental.config.PersonalRuntimeVerifier' -cp $ApplicationJar org.springframework.boot.loader.launch.PropertiesLauncher --checkpoint-fingerprint
if ($LASTEXITCODE -ne 0) { throw 'Checkpoint verification failed; preserve the runtime for review.' }
$before = ($beforeOutput -join '').Replace('CHECKPOINT_FINGERPRINT=', '')
if ($before -notmatch '^[A-Za-z0-9_-]{43}$') { throw 'Checkpoint verification output was invalid.' }
```

After the separately approved restart, stop the backend gracefully again, capture `$after` with the same command, and compare with `$before -ceq $after`. Do not print either value. Then start the backend normally again and verify health. A mismatch or verifier failure requires stopping this procedure and preserving the runtime for review.

Synthetic verification: `mvn -B verify` and `python -m unittest discover -s scripts -p test_personal_runtime_launcher.py -v`. The launcher tests replace Java with a mock; separate Java tests exercise real temporary H2 files and AES-GCM token validation. No real runtime, port 8081, OAuth or Google access is required.

## Personal storage layout

The launcher creates or reuses files only under the selected personal runtime directory, sets a generated `personal-*` tenant ID, and restricts the directory ACL to the current Windows user and SYSTEM. It uses separate Gmail and Drive token files and separate outputs, plus dedicated WhatsApp-simulation and unified H2 paths under that personal directory. A separately generated encryption key and local API token are stored there; the same personal encryption key protects both connector refresh-token files. None of these values or runtime records belong in Git.

The personal database and tenant are separate from the challenge runtime. Personal mode rejects synthetic Gmail/Drive snapshots and all WhatsApp ingestion. `POST /api/gmail/export`, `POST /api/unified/ingest?source=GMAIL`, and `POST /api/gmail/sync` are rejected in Personal mode before provider, file or repository work. Local-index Q&A that would read Gmail is rejected, and `/api/unified/search` rejects Gmail-specific and unfiltered reads that could expose existing Gmail rows. Source-filtered non-Gmail reads remain available under their existing policies. The protected explicit live Gmail Ask/Search and Full Email Viewer paths remain separate, approved, bounded and transient. The guards do not delete or migrate existing snapshot files, indexed rows, exports or backups. Challenge/SANDBOX export, ingestion, sync and local Q&A paths are unchanged. Do not manually copy an H2 database, token, export or backup between the profiles.

## Retention and deletion limits

The previously approved Personal policy specified seven-day snapshot, 30-day newly indexed Gmail record and 14-day log retention targets, with OAuth credentials retained until explicit revocation. The current live-only gate blocks new Gmail snapshot export/ingestion/sync but does not remove existing exports or Gmail rows. The five previously indexed real Gmail records remain subject to their legacy exemption unless separately approved. Each explicit repository upsert transaction still has a bounded purge of at most 100 expired Personal LIVE Gmail rows for the configured tenant and approved account, but the export-ingestion and sync API triggers are now gated; no cleanup trigger is promised by this gate. No scheduler or automatic provider request is introduced.

Current application source contains no logging calls for request payloads, provider response bodies or Gmail message content. API errors are reduced to fixed messages and allowlisted categories/reasons, and Spring's automatic error message and stacktrace inclusion are disabled. This source-level review does not establish the contents or retention of operating-system, shell, terminal, proxy or externally managed logs; the 14-day log target is not enforced by this application and needs an explicit host-level policy and verification.

Phase 1 records `first_ingested_at` and `expires_at` in the isolated unified H2 store for newly ingested Personal LIVE Gmail records. Timestamps are generated from the server UTC clock. A record is visible only while `expires_at` is strictly later than the current UTC instant; it is excluded at the exact expiry instant from repository search and therefore from deterministic Q&A, counts derived from search, and citations. Duplicate ingestion and updates preserve the original timestamps. An already expired identity remains in the store as a replay guard; older exports cannot replace or revive it. Records from before this metadata was introduced keep null retention columns and remain legacy, non-expiring records. No migration backfills or changes their metadata.

At exact expiry, eligible rows are removed from the live H2 table in the same transaction that writes a tombstone scoped by tenant, approved-account hash and hashed Gmail identity. Repository ingestion and sync upserts consult these tombstones, so stale exports or sync updates cannot restore purged identities; Step 17B now blocks the Personal HTTP ingestion and sync entry points, so those operations do not trigger new purges through the API. Tombstones have no expiry while old exports remain replayable; no bounded replay window has been established. The per-write purge is capped at 100 rows, so expired records remain excluded from retrieval immediately by the existing expiry predicate but may await later explicit repository writes before physical row removal. This SQL deletion is not forensic erasure: old backups or H2 storage artifacts may retain prior bytes. The 7-day export-file and 14-day log policies are approved targets but are not enforced; no cleanup task is scheduled. OAuth token revocation remains a separate provider-side action and does not delete indexed data. Selective/full-tenant deletion, backup cleanup, backup recovery, and restore validation remain unsupported. Recovery from a database snapshot predating a purge could restore data without its tombstone; such a snapshot must not be restored unless its tombstones are reconciled from a newer trusted ledger. Keep the runtime on an encrypted, access-controlled device; do not infer that expiry deletes exports, backups, paging files, logs, or provider-side mail.

### Gmail full-email viewer — backend Phase 1

Backend Phase 1 adds a protected, transient selected-message detail flow; it does not add a React viewer. Direct Gmail Q&A evidence may include an opaque `view_selection_id` when the authenticated request supplies a valid `X-Client-Session` UUID. The selection is retained only in a bounded in-memory registry for five minutes and is bound to the authenticated bearer-token fingerprint, browser session, Personal tenant and approved Gmail account. The browser must obtain a fresh per-message confirmation and call `POST /api/gmail/messages/view-approval` with `{ "selection_id": "…" }`; this returns a one-use, 60-second approval token. It then calls `POST /api/gmail/messages/view` with `{ "approval_token": "…" }`. Both POSTs require the existing bearer authentication, an exact configured loopback `Origin` (default Vite origins are `127.0.0.1:5176` and `localhost:5176`), and the same session header. Approval issuance and message retrieval are separate; the approval is consumed before any provider request, and cannot be reused.

The `/view-approval` and `/view` controllers start one monotonic 18-second local operation budget before request-body reading and downstream work. Each JSON body is limited to 1 KiB and read on the viewer-only bounded executor (two workers, two queued, reject-on-full); deadline checks run between bytes, and malformed, oversized, slow or incomplete bodies fail without issuing/consuming approval or starting OAuth/Gmail work. The caller stops waiting at the budget, subject to JVM scheduling and HTTP response delivery. A blocking servlet-stream read may remain in a worker after timeout; its slot remains occupied until the read exits, queued work stays capped at two, and further work is rejected. The same remaining budget covers approval consumption, OAuth state coordination/refresh, profile verification, full-message retrieval and MIME/body traversal. Viewer OAuth lock acquisition is timed; normal OAuth, direct Gmail Ask and sync keep their existing transport behavior. At most two Gmail REST attempts are permitted (profile plus one message), with 2 MiB per response and 4 MiB aggregate; no retry, pagination, attachment request or synchronization is performed. Viewer HTTP calls have request timeouts derived from the remaining budget and bounded streaming response bodies. The budget begins after servlet dispatch and does not cover connection/header waiting before the controller runs.

At timeout, the local response is a fixed, content-free `GMAIL_REQUEST_TIMEOUT`; active work and the HTTP exchange are cancelled best-effort, and any late result is discarded. Worker capacity remains occupied until the worker actually exits, so unresponsive local work cannot create an unbounded admission path. This does not guarantee immediate local thread/socket cleanup, nor does it guarantee that Google stops server-side processing immediately. No later provider operation is started once the shared budget expires. The transient DTO contains only subject, sender, recipient when available, received timestamp, readable body text, attachment display names, and explicit body/attachment incomplete, truncation and availability flags. Text/plain is preserved; HTML-only content is converted to inert readable text with non-display blocks removed. Attachment contents are never retrieved. MIME traversal is capped at 500 parts, body text at 262,144 characters, attachment names at 50 (200 characters each), and header values at 512 characters. Missing, malformed, externalized, oversized or unsupported body parts are represented as unavailable/incomplete rather than as complete content.

The API detail DTO contains no Gmail message/account IDs or citation internals, and its response inherits `Cache-Control: no-store` from the existing local API guard. The detail service has no repository or logging dependency: full details are not persisted to H2, exports, checkpoints, tombstones or logs. The short-lived selection/approval registry is in-memory only. Phase 1 had synthetic backend coverage. Phase 2 implements the React viewer, fresh per-message confirmation, transient detail state and close/return flow. It calls the authenticated approval endpoint and then the one-use view endpoint with the same browser-session UUID; cancellation makes no viewer request, and client calls have no automatic retry. The UI renders plain text only, displays attachment names but not contents, shows incomplete/truncated indicators, clears detail state on close/new search/disconnect/authentication failure, and uses no-store requests. Citation cards retain their visible reference and excerpt but no longer render internal source/account/version/locator identifiers. Synthetic frontend tests and a production build pass. Step 20CH/20CK later records user-reported readable Viewer content and close within the tested scope. No private message content is retained in these reports. That functional observation does not close P7 or establish historical-data cleanup. No synchronization or milestone status change follows from the Viewer implementation itself.
