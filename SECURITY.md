# Security and publication scope

This repository is a local portfolio/practice application, not a production authentication or hosting system. Do not expose the Java or Vite servers to the public Internet.

## Personal phase security gates

On feature/personal-connectors, PROJECT_RULES.md and PROJECT_ROADMAP.md govern a separately approved local Personal application. The inherited Challenge profile stays synthetic/sandbox-only. This document and enablement flags do not authorize new account operations; every live Gmail operation requires separate explicit user approval. A limited Personal Gmail OAuth connection and five-message export/index/search/Q&A sample, bounded direct Gmail Q&A, user-triggered sync, and viewer reads were previously observed and are retained as historical evidence only. The current backend gates Personal Gmail export, snapshot ingestion, history sync, indexed Gmail search and local-index Gmail Ask; explicitly approved live Ask/Search/viewer operations remain bounded and transient. No old export or H2 data is deleted by these gates. Personal Drive is disabled by default; Personal WhatsApp ingestion is currently denied. Existing Q&A remains deterministic and bounded where its source path is allowed.

Credential values, private identifiers and message/document bodies are excluded from governance evidence. Report pass/fail/counts and safe code/config references only. Do not inspect credential files, runtime databases or token/key contents without a task that explicitly authorizes the required local handling. No private content may be sent to external AI by default.

Personal Google credentials, encryption/API keys, token files, exports and H2 databases must remain outside every registered Git worktree and separate from Challenge storage. The launcher provides distinct per-profile keys and per-connector token files; Gmail and Drive currently share the Personal profile's encryption key, not the Challenge key. H2 and exports contain unencrypted local content; encrypted refresh tokens do not encrypt those records. Personal startup defaults to Gmail-only, with exact approved Gmail identity; Drive opt-in also requires approved account/root and isolated paths. Personal direct Gmail flows must not fall back to old H2 Gmail rows; the current controllers reject Gmail-specific and unfiltered unified-index reads. Existing legacy data remains subject to separately approved P7 cleanup and recovery controls. Search/Q&A must exclude Challenge synthetic records. Preserve these gates under all future changes.

For a credential exposure, stop provider use/publication, privately identify the affected client, obtain authorization for revocation/replacement, preserve recovery evidence without copying secrets into Git, and retest readiness. Do not rewrite history, rotate/delete files or change permissions automatically. Use the rollback procedure in docs/PERSONAL_CONNECTORS.md; deletion of data/backups and provider revocation are deliberate separate actions.

## Sensitive data

Keep Google Desktop JSON, OAuth grants, bearer/encryption keys, live records, databases, logs and screenshots of private data outside every checkout. Local runtime files use current-user/SYSTEM Windows ACLs when initialized with the helpers. Refresh tokens are encrypted; the local index itself is not an encrypted production database.

The public demo and committed fixtures are fabricated. Example addresses use reserved test/example domains. Real Gmail/Drive checks are optional, bounded and aggregate-only; the default public frontend demo never uses them. WhatsApp is simulated only and Q&A is deterministic, not an external AI service.

Enter the local bearer only into the trusted loopback UI. It stays in tab memory and is cleared on disconnect/401. A local browser, extensions or developer tools can still inspect memory/network; this is not an adversarial-browser security boundary.

The full-email viewer has a viewer-only monotonic 18-second local response cutoff covering controller request-body reading and downstream approval/OAuth/Gmail/MIME processing after servlet dispatch. Its 1 KiB JSON body is read on the bounded two-worker/two-queue viewer executor; incomplete/slow bodies time out without issuing or consuming approval or starting provider access. A blocked servlet-stream read may retain one of the two worker slots until it exits; queued admission remains capped at two, and excess work is rejected. Timeout errors are fixed and content-free; cancellation is best-effort and late results are discarded. This limits how long the backend handler waits to return a response, subject to JVM scheduling and HTTP response delivery. The cutoff does not cover connection/header waiting before servlet dispatch or promise immediate thread/socket cleanup; it also does not guarantee that Google stops remote processing immediately. Do not describe this as guaranteed termination of all work.

## Before publishing

Run python scripts/audit-publication.py from the repository root. It inspects every blob reachable from every local branch plus historical/index paths for known token/key patterns, non-example email addresses and sensitive artifact filenames. Commit/tag metadata is also checked for credential patterns and known private values; legitimate Git author identities are not treated as connector records. Optional --private-runtime and --oauth-client arguments compare known local credential/private values in process without printing them.

The scanner is a targeted review, not a general secret-detection guarantee or vulnerability certification. It does not inspect GitHub account permissions, unreachable local objects, every possible secret format or all dependencies for CVEs. Review staged content and history manually too. Do not post scanner findings containing actual secrets to a public issue.

.gitignore is defense in depth, not authorization to place private data in a checkout. Force-adding a secret can bypass ignores; the publication audit must pass before integration/publication. If a scan or merge fails, stop and report the blocker. Revoke any accidentally exposed credentials before discussing safe history remediation; do not push.

## Scope and limitations

The backend enforces a configured local tenant and current simulated WhatsApp group policy. It does not provide production user memberships or fresh per-file Google ACL checks. Results are snapshots; displayed UI evidence is not automatically invalidated after a backend policy change. Retrieved text is rendered as text and cannot authorize tools or external processing.

Google adapters are read-only, but read-only access still exposes private contents to the authorized local process. Keep OAuth consent minimal and do not enable HTTP wire/debug logs. Helpers default to the original developer's external D: paths; public synthetic startup demonstrates an external LocalAppData override. Review custom paths, permissions and symlinks/junctions yourself before any private use.

No public issue should contain credentials, private records or account identifiers. Use an available private maintainer channel for sensitive reports; if none exists, report only a non-sensitive description until a safe channel is arranged.

## Git identity privacy

All 16 unpublished original commits were rewritten with the owner-approved GitHub noreply email across all 10 local branches. Commit trees, messages, names and parent order were preserved. Repository-local author/committer email settings prevent accidental reuse of the global personal email. This was a privacy change, not credential revocation.

An external restricted-access recovery bundle, full Git-directory snapshot and pending-change snapshots are retained outside both worktrees. Old objects/reflogs may remain locally for recovery, but no old-history/backup refs are present among publishable refs. Never upload the recovery directory, copy the raw .git directory, push reflogs or restore old refs into a public repository. A future publication must use reviewed branch/tag refs rather than uploading a filesystem archive of Git internals.

Run `python -m unittest discover -s scripts -p test_audit_publication.py -v` for audit regressions. The audit uses separate object/category variables, inspects staged blobs as well as reachable history, and distinguishes ordinary Git identity metadata from credentials. Known private values are still blocked wherever found. This targeted audit is not a comprehensive DLP or vulnerability certification.
